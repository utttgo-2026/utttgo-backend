**Política SemVer aprobada por la responsable técnica (`MAJOR.MINOR.PATCH`, 2026-11-04):** la precedencia de prereleases como `-rc.1` es inferior a la versión estable correspondiente; mientras un componente sea `0.x`, su interfaz no se presume estable y **toda incompatibilidad se comunica explícitamente**. Un componente solo incrementa cuando cambia; una promoción entre entornos o un redeploy idéntico crea **otro registro DEP** sin falsificar cambios de versión. Nunca reutilizar una versión para artefactos distintos: reconstruir distinto exige nueva revisión/versión y commit registrado. La ventana concreta está aprobada abajo; falta cerrar el gate TASK-AUTH-007.

| Configuración por entorno | Cambio que exige migración coordinada/rompe compatibilidad. | Nueva clave/capacidad compatible. | Ajuste compatible; rotación de secreto registra **referencia/fecha sin valor** y revisión necesaria, nunca el secreto. |

**Compatibilidad backend ↔ móvil (política aprobada individualmente el 2026-11-04):** para cada versión backend registrar el rango de versiones móviles *probado* y el contrato REST admitido; para cada móvil, el rango backend/API requerido. **Mantener soporte para la versión móvil anterior durante al menos 30 días a partir de la publicación de una nueva versión móvil.** Solo una vulnerabilidad de seguridad que exija una medida extraordinaria **documentada** permite acortar ese plazo; registrar motivo, evaluación, decisión/autorización operativa y comunicación a clientes. Desplegar primero backend compatible con el móvil en uso y el nuevo; publicar móvil después. No retirar soporte mientras queden clientes admitidos sin ruta de actualización acordada. Una respuesta «aditiva» se prueba con serializadores y clientes antiguos (puede no ser compatible en modo estricto). No asumir que una app publicada en tienda puede revertirse instantáneamente. La ventana está definida como **mínimo**, no como fecha de retiro automático: registrar fechas y rangos *probados* por release.

**Identificador de despliegue aprobado por responsable técnica:** secuencia independiente `DEP-0001`, `DEP-0002`, …; un registro común/global es la implementación documental propuesta, pendiente de asignación operativa. No es SemVer, no modifica `/api/v1` ni se reserva por este documento. En **cada** intento/promoción registrar ID, resultado (`planificado`, `ejecutado`, `fallido`, `revertido`), entorno, fecha/hora UTC, versiones *efectivamente instaladas* y anteriores por componente (o «no desplegado»), commit SHA completo de cada artefacto/IaC, identificador/digest y build móvil si aplica, fichas/cambios incluidos, rango de compatibilidad probado, enlaces a CI/pruebas y revisión Terraform, responsable, aprobador, ventana, criterio y procedimiento de reversión. Nunca registrar secretos/tokens. Registro de cambios vincula cada versión a PR/commit, fichas API, naturaleza MAJOR/MINOR/PATCH y pruebas de compatibilidad. Si se promueve el mismo artefacto a otro entorno, se genera nuevo DEP y se anotan las revisiones de configuración/infra de ese entorno.

**Reversión (regla aprobada por responsable técnica):** la **responsable del punto 4** asume responsabilidad técnica de releases del backend y coordinación de su reversión, **no autorización automática para ejecutarla**. Antes del despliegue identificar la combinación previa *realmente probada* (backend + contrato + móvil compatible + configuración + infraestructura), su artefacto y referencias. Retroceder artefacto/configuración **solo** a una combinación previamente probada, con evidencia de compatibilidad y autorización operativa para el evento; para Terraform, revisar `plan` y estado remoto/bloqueo, **sin ejecutar reversión ni destruir infraestructura sin evidencia y autorización operativa correspondiente**, nunca `apply` inverso automático. Si no hay despliegue anterior, **detener promoción y corregir** mediante plan aprobado: no inventar rollback. Registrar aprobador operativo real y resultado en un nuevo DEP; las reglas de aprobación de producción siguen pendientes.
