> Versión documental **0.3.0** · 2026-11-04 · Estado: **CI-1 autorizada para implementación local por la responsable técnica, tras conformidad visible de tres participantes; ejecución remota aún no verificada**. TASK-AUTH-007/031 abiertos; no autoriza integración real ni CD.
> Autoridad: `docs/constitution.md` v2.3 → esta spec una vez aprobada → `plan.md` → `task.md`. Aplicación transversal a **todos** los módulos backend; no sustituye specs funcionales. Referencias: `docs/referencias-profesor-backend.md`.

## 1. Objetivo y alcance

Establecer gates verificables y evidencia para integrar cambios backend con seguridad desde el PR, evolucionar a integración real y, **solo con gates independientes y autorización**, promover releases. No crea endpoints, cambia contratos de siete candidatos ni incorpora infraestructura. La autorización de código CI-1 no equivale a comprobar una ejecución remota, cerrar `TASK-AUTH-031` ni al cumplimiento móvil.

**Tres etapas diferenciadas:**
1. **CI-1 sin servicios de aplicación externos ni nube:** GitHub Actions en PR hacia `main` y push a `feature/**`, evitando duplicados cuando sea viable. Ejecuta solución .NET 10 y tres suites locales con dobles; auditoría NuGet con política de fallo, secret scan obligatorio, SAST C# piloto no bloqueante y evidencia descargable. Restore y escáneres pueden consultar fuentes públicas de paquetes/advisories; una interrupción no equivale a un resultado limpio. Sin credenciales ni permisos de despliegue, publicación de imágenes o infraestructura real.
2. **CI-2 integración real no productiva:** MongoDB y Redis aislados (Testcontainers/Compose) y contratos de Supabase contra sandbox autorizado o dobles explícitamente rotulados; pruebas de seguridad distribuida, fallos y comportamiento real de adaptadores. Se define por SDD de módulos y aprobación específica; no se infiere de 320 tests locales.
3. **CD posterior:** artefacto versionado, aprobación, Terraform y promoción a Azure App Service en `dev/staging/prod`, health y reversión documentada a combinación realmente probada. No existe workflow ni autorización de ejecución de CD ahora.

Fuera: pipeline móvil implementada en este repositorio, despliegues AWS, EF/SQL, Pact, NBomber, Stryker, ChaosTest, umbrales arbitrarios de cobertura, secretos de prueba productivos, `terraform apply` o `destroy` en PR y destrucción programada. El orden de middleware de `Program.cs` no se toca.

## 3. Contrato de CI-1 para todo el backend

- Eventos **ratificados localmente**: `pull_request` hacia `main` y `push` a `feature/**` (convención de rama del equipo; ampliarla solo con ratificación). Ambos ejecutan todos los checks obligatorios, también en cambios exclusivamente documentales; ningún filtro de rutas puede omitirlos y dar verde. Optimizar duplicados solo si se demuestra que el push tiene PR abierto y el PR conserva sus checks requeridos; `concurrency` por rama/PR puede cancelar trabajo redundante, nunca ocultar un PR fallido. Runner efímero .NET 10, permisos de lectura por defecto; PR de forks sin secretos de nube.
- Usar `UTTTGO.Backend.slnx`: proyecto `src/UTTTGO.Api/UTTTGO.Api.csproj` y `tests/UtttGo.UnitTests/`, `tests/UtttGo.IntegrationTests/`, `tests/UtttGo.SecurityTests/`. La línea base reportada es **120+140+60=320 pruebas con dobles aprobadas localmente** (`docs/traceability-siete-endpoints.md`); el número no es umbral futuro ni acredita integración real.
- Ni el PR ni el push de CI-1 se declaran verdes si restauración, formato, build Release, alguna suite existente, escaneo de secretos o comprobación de auditoría NuGet fallan o no se ejecutan. `--no-build` sigue al build Release. **Política local CI-1:** vulnerabilidad NuGet `High`/`Critical` en dependencia directa o transitiva ⇒ fallo; `Low`/`Moderate` ⇒ informe y revisión (sin aprobar automáticamente la dependencia); fallo de red/fuente de advisories, datos ausentes o indeterminados ⇒ reintento acotado y luego **fallo de la auditoría**, sin etiquetar «sin vulnerabilidades». Excepciones requieren issue, evaluación y ratificación por el equipo; no silenciar alertas para lograr verde. SAST es piloto **informativo**, no bloquea hasta validación y nueva aprobación de reglas, resultados y política; nunca se anuncia como aprobado si no se ejecutó.
- Registrar versión SDK/herramientas, commit SHA, evento, estado por etapa y número real de pruebas; convertir TRX locales a **conteos descargables** sin publicar salida de pruebas ni datos personales. Resúmenes de escáneres sin tokens/PII, retención inicial de 7 días pendiente de política del repositorio. Reportes ausentes o suites omitidas se etiquetan «sin ejecutar», no «verde». Mantener trazabilidad requisito ↔ gate ↔ tarea ↔ artefacto; no publicar hallazgos crudos de secretos.
- Para cambios futuros en `infra/terraform`, solo cuando la ruta exista y su SDD se apruebe: `fmt -check`/`init -backend=false`/`validate` tras los checks previos, nunca `apply`/estado remoto/secretos en PR. No cambiar aquí Terraform ni AGENTS.

## 4. Seguridad, supply chain y aprobaciones

- **Secretos:** prohibidos en código, JSON, logs y artefactos. Selección provisional CI-1: Gitleaks OSS v8.30.1 (MIT), tarball oficial Linux x64 verificado con SHA-256; escanea commits de PR/push contra merge-base con `main` y árbol rastreado. Falla/ausencia bloquea, sin eco de hallazgos; canario inerte y runner Linux pendientes de evidencia final. La ratificación del *control* no aprueba integralmente el proveedor/versiones para release.
- **SCA:** auditoría nativa NuGet en restore/reporte de dependencias directas y transitivas, con normalización comprobada de severidad y códigos de salida para aplicar la política High/Critical anterior. Reintento acotado si falla la fuente pública; agotado, falla el gate por indisponibilidad (se distingue de vulnerabilidad), sin `--ignore-failed-sources` ni `tee` que encubra resultado. Sin umbral de cobertura ficticio. SBOM CycloneDX/Dependabot son candidatos posteriores, sujetos a evaluación.
- **SAST:** piloto informativo con Semgrep OSS v1.183.0 y **una** regla local C# de CORS permisivo; no implica cobertura JWT/Redis/Blob ni SAST integral. Sin Docker local disponible, hallazgo/falsos positivos y ejecución en runner pendientes. Resumen sin fragmentos de código, estado de herramienta fallida distinguido; solo nueva ratificación permite gate bloqueante. SonarCloud con token no es prerequisito.
- **Permisos:** `permissions: contents: read` como máximo necesario por defecto, sin `packages: write`, `id-token: write`, `pull-requests: write` ni credenciales de despliegue. Pin/revisión de procedencia de actions y herramientas; PR de forks no obtiene secretos. Solo autorización nueva permitiría ampliar permisos.
- **Integración/CD:** seguridad Redis fail-closed, rol local, SAS y moderación requieren pruebas correspondientes antes de release. OIDC hacia Azure, Key Vault, entornos protegidos, presupuesto, compatibilidad backend/móvil y aprobador por despliegue/reversión se diseñan y autorizan por separado. La constitución **ya fija Azure**: AWS requiere enmienda constitucional, no mera selección de workflow.

## 5. Quality gates y criterios de aceptación

| Gate | CI-1 | CI-2 / CD | Criterio de aceptación |
|---|---|---|---|
| SDD y revisión | Manual al inicio; automatización documental a ratificar | Reconciliación antes de release | Spec aprobada y plan/tareas consistentes; PR con revisor y trazabilidad; nunca aprobar a partir de checkboxes históricos. |
| Restore/formato/build/tests | **Bloqueantes** | Se mantienen más pruebas reales | 0 fallas; las tres suites ejecutadas, sin tests deshabilitados para obtener verde. |
| Secret scan | **Bloqueante**, Gitleaks provisional; piloto completo pendiente | Se mantiene | Ejecutado sobre commits y árbol rastreado; 0 secretos reales sin resolver, falsos positivos documentados sin exponer valores. |
| SCA / SAST | NuGet audit **bloquea High/Critical o resultado no verificable**; Semgrep C# **piloto informativo** | SAST bloqueante solo tras nueva aprobación; SCA se mantiene | Evidencia de severidad/transitivas, indisponibilidad distinguible; hallazgos SAST sin falso verde. |
| Integración de servicios | No exigida en CI-1; **deuda visible** | CI-2 bloqueante al aprobar módulos | Mongo/Redis no productivos, Supabase sandbox o dobles rotulados, tests de caída y seguridad sin falsos verdes. |
| Publicación/CD | **Prohibidos** en CI-1 | Solo tras gates documentados | Versiones/DEP, aprobación operativa, costos, dos instancias, entornos, salud/rollback probado; no desplegar ni destruir por calendario. |

No se aprueba un porcentaje de cobertura o latencia sin medición y nueva especificación NFR ratificada. El reporte del profesor de 45%/80% no es un umbral local. CI backend no satisface automáticamente la obligación móvil.

## 6. Escenarios Given/When/Then

- **CI-AC-01 (CI-R02/04):** Dado PR con spec aprobada y código backend, cuando CI-1 ejecuta restore, formato, build y las tres suites, entonces todos quedan reportados individualmente; una falla u omisión impide aprobar el PR.
- **CI-AC-02 (CI-R05):** Dado un secreto de prueba inerte detectado por el escáner en un PR de prueba, cuando corre secret scan, entonces falla el gate sin revelar el valor en logs/artefactos; no se exponen credenciales de nube al runner.
- **CI-AC-03 (CI-R08):** Dado que SAST aún no está habilitado con reglas validadas, cuando se publica el reporte, entonces indica «pendiente/informativo» y **no** afirma «Semgrep aprobado». Tras ratificación, un hallazgo de prueba ERROR provoca fallo verificable.
- **CI-AC-04 (CI-R02/06):** Dado que las pruebas usan dobles, cuando pasan las tres suites, entonces la evidencia indica «local con dobles» y TASK-AUTH-030/031 permanece abierta; nunca declara Mongo/Redis/Supabase reales verificados.
- **CI-AC-05 (CI-R01/03):** Dado CI backend verde y sin evidencia de CI móvil, cuando se evalúa el requisito académico, entonces se informa backend y móvil por separado y la obligación móvil queda pendiente.
- **CI-AC-06 (CI-R05/07):** Dado un PR o ausencia de aprobación operativa/costo/versionado, cuando se solicita `terraform apply`, publicación o despliegue, entonces no se ejecuta CD; solo un plan de etapa posterior con gates aprobados permite continuar.
- **CI-AC-07 (CI-R04):** Dado un cambio exclusivo de SDD, cuando abre PR, entonces se revisa su precedencia, estado y trazabilidad; no se etiqueta como CI aprobada una suite omitida por filtros de rutas.
- **CI-AC-08 (CI-R09):** Dado push `feature/**` sin PR abierto, cuando corre CI-1, entonces ejecuta los mismos controles; dado PR hacia `main` desde esa rama, entonces el PR conserva checks requeridos aunque se cancele/omita trabajo redundante del push.
- **CI-AC-09 (CI-R09):** Dado un paquete directo o transitivo con advisory High/Critical, cuando se audita NuGet, entonces falla el gate; dado servicio de advisories indisponible tras reintento, entonces falla **por indisponibilidad** y nunca reporta «sin vulnerabilidades».
- **CI-AC-10 (CI-R07/09):** Dado el acuerdo visible de tres participantes sobre la primera CI local y la autorización expresa posterior de la responsable técnica, cuando se implementa solo CI-1 (sin código funcional ni CD), entonces no se presenta TASK-AUTH-007 `[ ]` como bloqueo constitucional general ni como tarea completada; si se propone release o código funcional de fase 02, sus gates originales permanecen exigibles.
